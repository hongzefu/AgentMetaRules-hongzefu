## 一、一句话结论

Claude Code 的子代理是「一次性、并行、结果回收」模型：每次调用新建实例、全新上下文、只把最终结果交回主会话，交互会话里默认后台并行；默认与主会话共用工作目录，但官方提供 `isolation: worktree` 的子代理级 worktree 隔离。Codex 的子代理是「持久线程、可追加任务与互发消息」模型：代理以线程形式长驻，主代理可以追加任务、发消息、中断、恢复；所核实工具默认共享目录，改动立即互见，未提供自动创建子代理 worktree 的参数。主代理可以事先建立独立 worktree、指定路径与分支，再派子代理操作；有无自动隔离以当前宿主实际能力为准。两家材料均建议对写入型并行谨慎划分文件归属；2026-10-10 现行用户规则要求两宿主修改代理使用独立 worktree、验证并提交，由独立 Sonnet／Sol 审查、主代理整合及推送。

## 三、容易误读的八点

**1. Claude 的「近乎免费」只指等待时间，用量照算。** `CLAUDE.md` 所说「多 spawn 近乎免费」的依据是：总耗时由最慢的一个决定；派发本身不弹审批（"Launching the subagent doesn't itself prompt for permission."，译：启动子代理本身不请求权限，C:sub-agents）；后台运行不阻塞主会话（"Background subagents run concurrently while you continue working."，译：后台子代理在你继续工作时并发运行，C:sub-agents）。但用量一分不少："It also sends its own requests, which count toward the same usage limits as your main conversation."（译：它发出的请求与主会话计入同一用量上限，C:sub-agents）；"Running many subagents that each return detailed results can consume significant context, and each subagent spends tokens of its own while it runs."（译：运行许多各自返回详细结果的子代理会占用大量上下文，且每个子代理运行时都消耗自己的 token，C:docs）；"Running several sessions or subagents at once multiplies token usage."（译：同时运行多个会话或子代理会使 token 用量成倍增加，C:docs）。所以正本在「不设上限」之后补了「不以多开代理近乎免费为依据扩大范围或重复派发」（见 [`merge-decisions.md`](merge-decisions.md) B 节）。

**2. Claude 后台子代理仍能写文件，「只读」不是宿主保证。** 后台子代理的内置工具集明确包含 `Edit`、`Write`、`NotebookEdit`、`Bash`（C:sub-agents，原句见上表「能否写文件」行），被移除的只有 `AskUserQuestion`、`EnterPlanMode`、`ScheduleWakeup`、`Workflow`。「大部分情况不改代码」是 2026-09-26 的历史用法口径，2026-10-10 起现行规则统一按职责委派，探索只读、修改独立 worktree；只读，靠的是委派提示里的约束与选用 Explore / Plan 这类类型，不能把它当成宿主机制去依赖；一旦派出去的子代理要改文件，就必须按第 26 条同样的写入边界划清。 2026-10-01 补核：`isolation: "worktree"` 下宿主只拦 `Edit`/`Write`/`NotebookEdit` 写主检出路径与 git 重定向，Bash 绝对路径写主检出不拦（实测落地成功），所以即使隔离也只能叫「部分硬拦」，合并前主会话必须再查主检出 `git status --short`。

**3. Claude 的 worktree 默认不是基于当前 HEAD，有改动也不会自动合回。** `isolation: worktree` 的副本 "branched by default from your default branch rather than the parent session's `HEAD`"（译：默认从默认分支分出，而不是父会话的 HEAD，C:sub-agents）；只有 `worktree.baseRef: "head"` 才基于在途工作："Use this when isolating subagents that need to operate on in-progress work."（译：当被隔离的子代理需要在进行中的工作之上操作时使用此项，C:worktrees）。有改动的 worktree "stays on disk until the periodic sweep … can remove it without losing work"（译：留在磁盘上，直到周期清扫能在不丢失工作的前提下删除它，C:worktrees）——官方没有说会自动合回主检出，整合要由主代理自己做。 2026-10-01 实测：不设 `baseRef` 时 benchmark 的 worktree 从 `origin/HEAD`（默认分支 commit 2.24）分出、与当前分支 12.285 差十个大版本；设 `"head"` 后下一个子代理即基于当前 HEAD，不需重启会话。合回的落法见 `CLAUDE.md`「计划执行模式」：子代理在自己分支 commit，主会话 `git merge --no-ff <TIP sha>`。

**4. Codex 默认共享目录，修改代理须明确安排独立 worktree。** 所核实系统提示写明一个代理的编辑立即对其他所有代理可见（X:prompt）；当时 git-worktrees 页只讲对话／定时任务级 worktree（X:git-worktrees），`spawn_agent` 未提供 cwd 或 worktree 参数（X:spec），这不等于子代理不能操作主代理事先建好的 worktree。有无自动隔离以当前宿主实际工具为准；用户规则要求主代理指定绝对路径、基线与专属分支，子代理每次写入、暂存或提交前核实工作区根与分支。2026-10-10 起两宿主代码／文件修改代理统一独立 worktree，不再共用主检出写代码；独立 worktree 子代理可验证并提交专属写集，全部子代理不 push、不合主分支。worktree 不是权限沙箱，产物、环境与计算资源也须另行划界。

**5. `close_agent` 只在 V1 工具集里。** V1 下 "Completed agents remain open and count toward the concurrency limit until closed."（译：已完成的代理在关闭前仍保持打开并计入并发上限，X:spec），所以要主动 `close_agent`。V2 工具集（X:plan）没有 `close_agent`，只有 `interrupt_agent`；空闲子代理由宿主处理：`residency.rs` 的 `is_unloadable` 判定状态为 Completed / Errored / Interrupted、没有活动回合且邮箱为空的子代理，在容量不足时自动卸载（X:residency）。写规则时不要要求 V2 下「手动关闭代理」。

**6. Codex 并发数到底含不含主代理，以实测为准。** 文档写 "Cap concurrently open spawned-agent threads, excluding the primary"（译：限制同时打开的派生代理线程，不含主代理，X:docs）；系统提示却写 "up to {N} agents can be active at once, including you"（译：最多 {N} 个代理可同时活动，包括你自己，X:prompt）；源码 V2 默认 `DEFAULT_MULTI_AGENT_V2_MAX_CONCURRENT_THREADS_PER_SESSION = 4` 且内部计数含主线程（X:src）。本机 `~/.codex/config.toml` 设 `max_concurrent_threads_per_session = 16`，2026-09-26 新建 SSH App 任务实测 16 个子代理与主代理同刻 running、第 17 个 `collab spawn failed: agent thread limit reached`（实测）——即配置值 16 对应 16 个子代理，不含主代理。累计创建数不能说成同时运行数（第 26 条「并发容量」）。

**7. 改配置不会给旧任务扩容。** 旧任务树的 `AgentExecutionLimiter` 用 `OnceLock/get_or_init` 初始化，正式配置热重载只更新配置、不替换已有 limiter，旧任务原有的 4 槽不承诺即时扩容（实测）。改了 `max_concurrent_threads_per_session` 之后，要在新建的任务里才能拿到新容量；也不得另开顶层任务去规避容量限制（第 26 条）。

**8. 已从当前文档移除的机制不写进规则。** `spawn_agents_on_csv` / `report_agent_job_result`（PR #34413，2026-07-20 移除）、`nickname_candidates` 都已移除；`agents.max_depth` 当前文档里没有了，只剩旧文档 "agents.max_depth defaults to 1"（X:old）和 V1 源码常量 `DEFAULT_AGENT_MAX_DEPTH = 1`（X:src）。同理，`agents.max_threads` 只是 `agents.max_concurrent_threads_per_session` 的旧别名，规则里统一写新名。

## 四、现行统一角色政策与 Harness 生命周期（2026-10-10）

本节描述当前用户规则，权威入口是 [`AGENTS.md`](../AGENTS.md) 第 26 条；[`CLAUDE.md`](../CLAUDE.md) 只保留 Claude 的操作。旧材料里的「默认只读」「计划外主会话写代码」「表外不派」和运行不能提交 job 已不再是现行通用政策。宿主操作、真实容量、工具权限不由这次文字修订改变。

| 职责 | Claude 档位 | Codex 档位 | sled-vail 实际模型 | 委派边界 |
|---|---|---|---|---|
| 探索、检索、定位、日志与信息读取 | `haiku` | Luna | `gpt-6-luna` | 只读，主代理按需大量并发，不预列／逐项审批；覆盖不全再分片派小模型，不升档探索 |
| 规划、写代码、修改文件、解冲突 | `opus` | Sol | `gpt-6.1-sol` | 明确代码委派；修改文件独立 worktree，同文件单 owner |
| 运行、提交新 job／启动已有 job 工作负载 | `opus` | Sol | `gpt-6.1-sol` | 明确版本／命令／资源／预算；立即回 JobID，状态不明先核查；不能改代码或自行转修复 |
| 审查、对抗验证、文档与代码评审 | `sonnet` | Sol | `gpt-6.1-sol` | 固定范围独立审查，失败交回修改代理续改后重审 |

每次显式指定模型，不继承模型绕过规则；大角色不降档，子代理／递归子代理档位不高于主请求。职责与主请求上限、宿主限制或模型可用性冲突时停并报告，不静默换档；推理强度独立选择。Aspen 继续只用 `gpt-5.6-sol`／`gpt-5.6-luna`，禁止 Terra 和 GPT-6 等其他版本，映射与验证见第 26 条及 [`codex-aspen-gpt56-roles.md`](codex-aspen-gpt56-roles.md)。规则修订不代表角色配置安装已更新。全历史 fork 若不能覆盖模型，用 `fork_turns="none"` 与自含说明；这是相应宿主的工具限制。Workflow 的角色也按同一张表，取消人工最多 3 次 opus 限制，Workflow 逐次审批与实际工具限制保留。

**派发与隔离**：有计划尽量跟随，在已有实施授权内主代理可调整职责、数量、依赖和整合顺序，说明原因与实际文件归属，不反复问。没有计划分工时，先明确委派再派：代码委派含目标、上下文、工作树／基线／分支、可写文件、禁触、依赖、交付和验收；运行委派含完整命令、确定版本、位置、资源预算、输出、起跑判据、最长等待和失败重试上限。探索自主派发不等于代码／运行实施授权，不扩大范围、费用、保护代码或 reset／轨迹预算。

两宿主修改代理统一独立 worktree。流程是主代理指定工作树与边界 → 子代理改专属写集、验证并作 `sub/<编号>:` 提交 → 独立 Sonnet／Sol 审固定 `BASE`／`TIP` → 失败交原代理续改以新提交重审 → 主代理 `--no-ff` 整合、保留子提交 → 整体验证与审查通过后统一 push。子代理每次写入／暂存／提交前核对工作树与分支，不 push、不合主分支。产物／资源隔离另行规定，worktree 不是权限沙箱。

**运行与修复**：运行代理可按明确授权提交新 job 或启动已有 job 工作负载，立即回 JobID；提交状态不明先核查，禁止重复提交。主代理唯一管理资源、预算、监听、接续和清理。运行代理不得改代码／配置／启动脚本／依赖／参数／补丁，不得转成代码代理或派修复代理。发现需修代码交主代理另派独立修复代理；修复经审查、验证、整合后，主代理再交确定版本与命令续跑。授权程序的日志、结果和预算账本更新允许写入指定路径，交回如实列明，不要求「未改文件」这种不真实承诺。

**唯一保留的策略差异是 Harness 生命周期**：Claude 在同一决策点按批派发，一份结果交回即结束，下一决策点按需新派，必要续接以实际工具为准；Codex 持久化复用同职责代理并通信追加任务。两者的工具调用、真实容量和权限按宿主能力；不把统一角色政策等同于强行统一生命周期。

| 宿主 | 生命周期 | 操作入口与历史依据 |
|---|---|---|
| Claude Code | 一次性、按批交回；不搭长期代理网络 | `CLAUDE.md` Agent／worktree／运行型操作；2026-09-26 用户原话「一般在一个时间节点上同时放出一堆agent 然后用完即废弃」；2026-10-01 worktree 隔离与合并实测仍见第三节 |
| Codex | 持久化、同职责续用；职责结束或需腾槽才关闭 | 第 26 条宿主专节；V1／V2 的工具差异与 2026-09-26 16 子代理实测仍见第二、三节 |

## 五、复核方法

1. **读固定标签源码**（`rust-v0.157.0`，不读 main，避免漂移）：

   ```bash
   gh api -H "Accept: application/vnd.github.raw" \
     "repos/openai/codex/contents/codex-rs/prompts/src/multi_agent_instructions.rs?ref=rust-v0.157.0"
   gh api -H "Accept: application/vnd.github.raw" \
     "repos/openai/codex/contents/codex-rs/core/src/tools/handlers/multi_agents_spec.rs?ref=rust-v0.157.0" \
     | grep -n "disjoint write set\|wait_agent very sparingly\|Completed agents remain open"
   ```

   其余文件把路径换成 `codex-rs/core/src/agent/role.rs`、`codex-rs/core/src/tools/spec_plan.rs`、`codex-rs/core/src/agent/control/residency.rs` 即可；通用形式为 `gh api -H "Accept: application/vnd.github.raw" "repos/openai/codex/contents/<路径>?ref=rust-v0.157.0"`。
2. **读官方文档**：用 WebFetch 抓取「参考」里的各文档 URL，按本文引用的英文原句逐条检索。文档会改版（`max_depth`、`spawn_agents_on_csv` 就是例子），复核时注明抓取日期；旧版表述用 Wayback 快照核对。
3. **本机 Codex 并发配置**：

   ```bash
   grep -n -A3 '^\[agents\]' ~/.codex/config.toml
   ```

   关注 `max_concurrent_threads_per_session`（本机为 16）。配置能解析不代表容量生效，实际容量按 [`codex-app-ssh-multiagent.md`](codex-app-ssh-multiagent.md) 的复验步骤在新建任务里验收。
