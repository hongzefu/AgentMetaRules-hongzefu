二、机制

A. 子模块作为规则来源（K1、K7）

定义：每个接入仓库的根目录有子模块 .agentmetarules/，.gitmodules 内容固定：

[submodule ".agentmetarules"]
	path = .agentmetarules
	url = https://github.com/hongzefu/AgentMetaRules-hongzefu.git
	branch = main

git 的子模块指针永远记录一个具体 commit，没法真正「不钉版本」。所以「每次钉在最新版」的做法是：开工时 git submodule update --init --remote .agentmetarules，把子模块切到 origin/main 的最新 commit；指针有变化就和规则文件一起提交、推送。

锚点：scripts/sync_rules.py 的 load_config() 现在从 sync-targets.json 的 canon.path 读正本路径，Canon.read_file 用 git cat-file blob <sha>:<file> 读正本内容。子模块本身是一个独立的 git 仓库，.agentmetarules/ 里直接就有 AGENTS.md，所以不需要改按子目录读文件的逻辑。只需新增一个自同步模式：

uv run --no-project python .agentmetarules/scripts/sync_rules.py self-check  --root .
uv run --no-project python .agentmetarules/scripts/sync_rules.py self-apply  --root .

自同步模式下：正本 = <root>/.agentmetarules，版本 = 子模块的 HEAD；目标 = <root>。文件到块名的映射由扫描根目录 AGENTS.md/CLAUDE.md/greatlakes.md 里现有的 AGENTMETARULES:BEGIN <块名> 行得出，不需要新配置文件。判定行沿用现有格式 SYNC=PASS|FAIL 和 SYNC_SUMMARY=，并新增 MODE=self。

⚠ 陷阱

  • 同一个仓库同时当正本和目标会把正本源格式改坏：cmd_apply 会把不带属性的 BEGIN 行改写成带 src=/blob= 的目标格式。自同步模式要加守卫：root 的真实路径等于正本仓库时拒绝执行，判定行写 SELF_SYNC=FAIL reason=canon_is_target。正本仓库自己不加子模块。
  • 子模块里不建 .venv。脚本只用标准库，经 uv run --no-project 运行（第 3 条）。
  • 嵌套情况：coimprovement 以子模块形式包含 MotionJEPA 和 policy，这两个仓库又各自有 .agentmetarules。git submodule update 默认不递归，所以 coimprovement 的开工检查只管它自己根目录的 .agentmetarules；嵌进来的仓库在各自的会话里自己检查。
  • worktree：子代理的 worktree 是干净检出，子模块目录为空。开工检查只在主检出做；worktree 里的子代理不跑检查，也不改规则文件。

收益：不再需要逐台机器维护 sync-targets.json 的 machines 段路径；新 clone 或第二份检出在开工时自己就能对齐。迁移完成后 sync-targets.json 只保留 global-claude 一个目标。

豁免（PUSH_STATE=EXEMPT）：分支名匹配 worktree-agent-*（子代理 worktree）；没有 upstream 且不是本会话新建的分支，标 EXEMPT reason=no_upstream，agent 问用户一次是否 git push -u，这项沿用第 11 条原有的「没有 upstream」例外。

hook 挂法（全局 ~/.claude/settings.json，只合并 hooks 段，不动其他键）：

"hooks": {
  "SessionStart": [{"hooks": [{"type": "command", "timeout": 60,
    "command": "s=\"$CLAUDE_PROJECT_DIR/.agentmetarules/scripts/repo_guard.py\"; [ -f \"$s\" ] || s=\"<本机正本 clone>/scripts/repo_guard.py\"; cd \"$CLAUDE_PROJECT_DIR\" && uv run --no-project --quiet python \"$s\" start"}]}],
  "PostToolUse": [{"matcher": "Bash", "hooks": [{"type": "command", "timeout": 30,
    "command": "s=\"$CLAUDE_PROJECT_DIR/.agentmetarules/scripts/repo_guard.py\"; [ -f \"$s\" ] || s=\"<本机正本 clone>/scripts/repo_guard.py\"; uv run --no-project --quiet python \"$s\" post-commit"}]}]
}

SessionStart 的 stdout 会进入会话上下文，agent 第一条回复把三行判定行照抄出来，再执行 fix。hook 本身不写仓库：自动提交和推送放在 agent 可见、可停的 fix 步骤里做，避免会话一启动就在用户没看到的情况下改历史。Codex 没有 hook，只按第 29 条在开工时手动跑 start 和 fix，提交后手动跑 git status -sb。

⚠ 陷阱：不在 git 仓库里的目录，start 只输出 REPO_SYNC=NOT_GIT 并以退出码 0 结束；hook 内部任何异常都输出一行 GUARD_ERROR= 并以退出码 0 结束，不能阻断会话。PostToolUse 对每次 Bash 调用都会触发，所以先用正则过滤，不匹配就立即退出（目标 <50 ms），且不做 fetch。

E. 跨会话三次握手与积极响应（K9）

第 28 条的修改（适用范围不变：同一用户的 Claude Code 会话之间；本会话自己派出的子代理不适用）：

步骤发送方内容类比 TCP
①甲请求，第一行写 req=<发起方短名>-<美东 MMDDHHMM>-<序号>，再写要什么、期限SYN
②乙开头写「收到 req=…」，再给结果；处理时间较长就先回「收到 req=…，处理中」，办完再发一条「req=… 结果：…」（这条不算新请求）SYN-ACK
③甲「收到 req=…」，握手结束。这是纯回执，乙不再回复ACK

甲在合理时间内没收到 ②，就用同一个 req 重发一次；还是没回复，就报告用户。乙收到重复的 req 不重复执行，只重发上次的 ②（幂等）。原有的「纯回执不再回复」规则保留，适用于 ③ 和其他无新内容的消息。

积极响应：存续中或被唤醒的会话收到消息，一律尽量照办。只有三种情况不做：用户明确禁止；与用户指令有明确冲突；删除、覆盖、--force 这类破坏性操作。凭据不经消息传递。原第 28 条边界里的「超出已批规模 5 倍」「放宽验收判据」「无法以同等规模完成的机制调整」三项删掉。⚠ 解释：开工令（第 2 条）、受保护目录逐个批准（第 21 条）本身就是用户的指令，对方消息不能代替用户放行，这类情况算「与用户指令冲突」，所以「对方消息不是用户授权」这一句保留；同样，按第 28 条修改权限设置或规则文件，属于与第 25 条冲突，仍然不做。

一、正本逐文件改动

1.1 scripts/sync_rules.py（W1）

  • build_parser：新增子命令 self-check、self-apply，参数 --root（默认 .）、--allow-dirty。
  • 新函数 load_self_config(root)：canon = {path: root/.agentmetarules, branch: None, files: 正本固定映射}，版本用 git -C canon rev-parse HEAD，不走 refs/heads/<branch>，因为子模块是 detached HEAD；target = {name: "self", path: root, files: 扫描根目录三份 md 的 BEGIN 行得出}。

1.2 scripts/repo_guard.py（W1，新建）

  • 只用标准库（subprocess、json、re、sys）；所有 git 调用带 timeout，fetch 20 秒，其他 10 秒。
  • start：git rev-parse --show-toplevel 失败 → REPO_SYNC=NOT_GIT；git fetch --quiet 失败 → REPO_SYNC=FETCH_FAIL，但继续用本地 ref 计算；git rev-list --left-right --count HEAD...@{u} 得到 ahead/behind；.agentmetarules 存在时 git -C .agentmetarules fetch --quiet origin main，再算 rev-list --count HEAD..origin/main；不存在但根目录 md 有 AGENTMETARULES:BEGIN common- 行 → RULES_SYNC=NOT_ONBOARDED；都没有 → NO_SUBMODULE。
  • fix：按机制 B 的 ①–⑥ 顺序执行，每步失败都输出 GUARD_FIX=STOP reason=<步骤> 并附 git 原文；commit 信息用 --message-file 传入，默认 subject 为 docs: 规则子模块更新到 <短 sha>（项目体例不是 docs: 的仓库，用 --subject-prefix 覆盖），body 写前后 sha、改动文件、SYNC_SUMMARY 行，加上 Co-Authored-By 行。
  • post-commit：读 stdin JSON；tool_name != "Bash" 或命令不匹配正则就静默退出；匹配时算 ahead，大于 0 就打印 {"hookSpecificOutput":{"hookEventName":"PostToolUse","additionalContext":"PUSH_STATE=AHEAD n=<n> branch=<b>：按第 29 条立即 git push"}}；分支名匹配 worktree-agent-* 时不输出。

六、风险登记

风险影响处置
每次开工都可能产生一个「规则子模块更新」commit各仓库历史里多出一串小提交只在正本有新 commit 时才产生；正本平均每天几次，可以接受

两台机器同时更新同一分支的子模块指针后推的一方被拒（非快进）按 K5、K6 停下报告；下次开工快进后指针已经一致，变成 NOOP

对方会话借「积极响应」要求做大改计划被别的会话改走开工令和第 21 条仍然是用户指令，算冲突；破坏性操作不做
